> Verbatim dated notes, original order. Read this file when the task touches: guardrails.py, order_gate.py, any BLOCK/WARN. Dated notes here still override older ones; CLAUDE.md core rules win on conflicts.

- **Guardrails / checks and balances (2026-11-09, user: "think of all guard rails"; applies to ND and AZ).** Each workspace has its OWN copy (no shared code, per the separation rule) of `scripts/guardrails.py` (+ `test_guardrails.py`, `order_gate.py`, `data/guardrails_config.json` thresholds, `data/trading_halt.json` kill switch). They run at the end of `refresh_dhan.py` / `refresh_zerodha.py` and write `data/guardrails.json` (`status` OK/WARN/BLOCK_SYMBOLS/BLOCK, `global_block`, `per_symbol_blocks`, `findings[]`). Levels: BLOCK = no order for that stock (symbol null = every order), WARN = look before ordering, INFO. Checks (ids): F1 market-data lag (1 session WARN, 3+ BLOCK), F2 holdings age, F3 signals older than holdings, F4 order snapshot age, F5 the independent Yahoo cross-check disagrees with >= 25% of the signals (>= 4 signals) = GLOBAL BLOCK (suspect prices: a partial same-day bar while the market is open, a hole in the history, a bad feed; fewer flags = WARN and those stocks are blocked individually); I1 NaN/inf, I2 position rows (qty/avg/cmp positive, P&L% recomputed, signal qty/avg == holdings), I3 holdings vs fill ledger (Dhan only: recent unsettled buys = one aggregated WARN, anything else = BLOCK), I4 stock in two signal lists, I5 hedge/excluded stock as a signal, I6 fill sanity (qty/price > 0, sells <= buys, price within 25% of market), I7 bought in the last 3 days but not in holdings -> never entry/add again (the ticket builder only sees holdings, so without this it could double-buy); S1 exit must be red, S2 add-on green + P&L beyond the trigger (ND -6%, AZ any loss) + 7-day cooldown + qty >= 1, S3 entry green + not held + qty >= 1 + (ND: at the 52-week high; AZ: flip within 6 trading days), S4 (min-1-share overspend: REMOVED 2026-11-16, the user is fine with a position above the tier size; check, config key and test removed in both copies), S5 too many entries (WARN) / mass exit (>= 5 and >= 20% of positions flip red at once = suspect data, BLOCK); C1 deployed vs base, C2 single stock > 20% / sector > 40% of deployed, C3 pending buys + planned entries vs base; O1 pending SELL > held (oversell), O2 duplicate pending orders, O3 pending order with no signal; P1 expiry week, P2 no lot size, P3 open option exit or strike-breach alert, P4 short call not covered by shares (ND); X1 no import from the other broker's folder; H1 trading halt. `order_gate.py` (used by `build_order_ticket.py` and `build_share_ticket.py`; the future AZ order skills must call their own copy) refuses to build any ticket when `guardrails.json` is missing/for different signals, when a global block exists, when the stock is blocked, or when a batch exceeds 40 orders / 25% of the capital base (`--allow-big-batch` only on the user's explicit request). The pages show the result as a "Guardrails" banner (`dhGuardHtml`, per workspace). RULES: add a check by adding it to BOTH copies' `evaluate()` + `test_guardrails.py` (every check needs a failing-input test) and keep thresholds in `guardrails_config.json`; never weaken a BLOCK to make a refresh pass - fix the data; never flip `trading_halt.json` unless the user asks. Known benign findings: I3 settlement lag (Dhan holdings update a session after AMO fills), cross-check flags while the market is open (Yahoo's partial same-day bar vs the previous close's signals), the Dhan MCP tradebook reports qty 0 for every fill (take the fill price from the tradebook and the quantity from the order book, where TRADED), and Zerodha session/Dhan token expiry (log in again each day).
