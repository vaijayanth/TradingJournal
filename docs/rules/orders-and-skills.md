# Orders and skills (rules split out of CLAUDE.md on 2026-11-25)

> Verbatim dated notes, original order. Read this file when the task touches: placing orders, editing order skills. Dated notes here still override older ones; CLAUDE.md core rules win on conflicts.

- **Order placement (Dhan, stocks only).** Skills `dhan-order-entry` (entry + add-on BUYs) and `dhan-order-exit` (full-position SELLs on Supertrend red), user-invoked only, never options. They place AFTER-MARKET (AMO) LIMIT / CNC orders for the next trading day (run after the close, never during market hours; BUY limit = the signal day's HIGH capped at close +2% (user rule); exit SELL = AMO MARKET order at the next open (user rule: every exit signal is exited, no price guard blocks it); fills are recorded by the next trading day's /refresh-dhan because the MCP tradebook is today-only) through the Dhan MCP `trading_agent_tool` only after `scripts/build_order_ticket.py` builds the tickets from `dhan_live_signals.json` (the sole source of what may be traded; it refuses stocks without a signal, hedge-portfolio symbols and data older than 3 days), a live-price guard (3%), a funds check and an explicit per-batch user confirmation; fills are then recorded with `append_fills.py` + `/refresh-dhan`. Naming convention: broker prefix (`dhan-` now, `zerodha-order-entry` / `zerodha-order-exit` later with their own logic). The website itself never places orders (a static page cannot hold a trading token). The exact `place` payload fields are inferred from the margin tool's schema (which works for CNC equity) and have not been exercised yet - the first real order is the test.

- **Investment-portfolio share strategy + orders (Dhan, shares only; user's rules 2026-11-08).** Exit = Supertrend red AND the position in profit (sell the whole position; a red loser is held). Entry = Supertrend flips red to green on a stock not held: size = the last position's capital PLUS the profit made on that stock in the previous trade, floored to whole shares (min 1) - from `data/invest_trades.json`, which `scripts/invest_trades.py` fills (`pending` at exit placement captures the capital; `fill` after the SELL fills books profit, gross of charges); a stock with no recorded previous trade has no defined size so the user states the quantity. Averaging = once a week when green and the open loss is worse than -6% (1/10 of the holding). Engine: `compute_covered_call.py` (`shares.exits`, entry `qty_to_buy`). Skills `dhan-invest-order-entry` / `dhan-invest-order-exit` (user-invoked, never options, never dh252 stocks) use `scripts/build_share_ticket.py`; same AMO conventions as the dh252 skills (BUY limit = day high capped at close +2%; SELL MARKET at the open). The Dhan MCP's pre-trade funds check is broken (sign-flipped shortfall), so `preflight:false` only after the user's yes. Option orders get their own separate skill (not written yet).

- **zerodha-order-entry skill (2026-11-09, user):** `.claude/skills/zerodha-order-entry` (AZ only, user-invoked) places AFTER-MARKET (`variety: amo`) LIMIT / CNC / NSE BUY orders for the AZ entry and add-on signals through the Zerodha MCP `place_order`, from `zerodha-live/scripts/build_order_ticket.py` (own copy, no Dhan code; guardrail gate, cross-check block, batch caps; quantities from the engine). Same limit rule as ND (signal day's high capped at close +2%), one explicit yes per batch, first order checked before the rest. Fills are recorded by the next /refresh-zerodha (`zerodha_trades.py buy [--entry]`). Zerodha has no exit order skill yet.
- **zerodha-order-entry lists only the freshest flip day (2026-11-09, user):** `build_order_ticket.py` shows entry signals only for the most recent flip day that has an orderable signal (today first, else yesterday, then 2 and 3 trading days ago); older flips are hidden unless `--all-days`; add-ons are always listed; a cross-check-blocked signal does not count. The Live Trading page still shows every flip in the 3-day window.
- **AZ add-on rule = ND's (user, 2026-11-09):** an AZ position gets an add-on when Supertrend is green and its P&L is -6% or worse (1/10 of the quantity, minimum 1, once every 7 days), NOT on any loss. `compute_zerodha_live_signals.py` ADD_TRIGGER_PCT = -6.0, `guardrails_config.json` add_trigger_pct -6.0 (guardrail S2 now blocks an add-on above -6%), page cfg addTriggerPct -6; the rule text in the refresh-zerodha and zerodha-order-entry skills matches.
- **zerodha-order-exit skill (2026-11-09, user):** `.claude/skills/zerodha-order-exit` (AZ only, user-invoked) places AFTER-MARKET (`variety: amo`) MARKET / CNC / NSE SELL orders for the whole position of each AZ exit signal (Supertrend red, grandfather rule applied by the engine), from `zerodha-live/scripts/build_order_ticket.py exit` (each ticket carries avg_cost and entry_date and a WARNING when a short CALL is open on the stock). Before placing it records `zerodha_trades.py pending` (avg cost); the next /refresh-zerodha books the fill. If Zerodha refuses a market AMO the skill stops and offers a LIMIT (close x 0.98) only after the user agrees. Never partial, never options. Not yet exercised with a real order (no exit signal today).
- **zerodha-order replaces zerodha-order-entry and zerodha-order-exit (2026-11-09, user):** one skill, `.claude/skills/zerodha-order`, places AZ AMO orders from ONE numbered list built by `zerodha-live/scripts/build_order_ticket.py all` (exits first - SELL MARKET, tag AZEXIT; then entries - BUY LIMIT, tag AZENTRY; then add-ons - BUY LIMIT, tag AZADD). Every rule in the two earlier CLAUDE.md notes (freshest flip day only, -6% add-on, whole-position exits, pending avg-cost record before an exit, short-call warning, limit = day high capped at close +2%) is unchanged; only the skill names changed. The old two skill folders are deleted.
- **zerodha-order runs in stages (2026-11-09, user):** the skill takes ONE group at a time in this order - 1) exits, 2) add-ons, 3) entries. For each group it lists only that group (`build_order_ticket.py exit|addon|entry`, numbering restarts at 1), asks 'go ahead with all N or which to exclude?', shows the ticket and waits for 'yes, place these', places, then VERIFIES every order in `get_orders` before the next group is even listed. A rejection or a missing order stops the run. No combined confirmation across groups.
- **dhan-order replaces dhan-order-entry and dhan-order-exit (2026-11-09, user):** one skill, `.claude/skills/dhan-order`, runs the dh252 stock orders in STAGES like `zerodha-order`: 1) exits (SELL MARKET AMO), 2) add-ons, 3) entries (BUY LIMIT AMO, limit = signal-day high capped at close +2%). For each group it lists only that group (`dhan-live/scripts/build_order_ticket.py exit|addon|entry`, numbering restarts at 1), asks 'go ahead with all N or which to exclude?', shows the ticket, waits for 'yes, place these', places (the broken Dhan preflight check is overridden only after the user's explicit yes), then VERIFIES every order in the order book before the next group is listed. The old two skill folders are deleted; the Dhan investment-share skills (dhan-invest-order-entry / -exit) and `dhan-superorder` are unchanged. The Dhan builder now also has an `all` mode (used only for the overview counts).
- **Empty groups are announced (2026-11-09, user):** in `zerodha-order` and `dhan-order`, a group with no rows (no exits / add-ons / entries) is never skipped silently: the skill says explicitly 'no <group> today', then asks 'Move ahead to <next group>?' and waits for the user's yes before listing the next group; after an empty entries group it says the run is finished.
- **Entries are today's signals only, ND and AZ (user, 2026-11-09, replaces the 'freshest flip day' fallback):** `build_order_ticket.py entry|all|buy` lists an AZ entry only when its flip is today (age 0) and an ND entry only when its 52-week-high day equals the latest session; anything older is a missed day and is never ordered (`--all-days` shows it, only on the user's request; the skipped line says why). Add-ons and exits are unaffected. The Live Trading pages still show the whole 3-day AZ window.
- **AZ entry window = today (user, 2026-11-09):** `ENTRY_WINDOW_TRADING_DAYS = 0` in the engine, guardrail `entry_window_days` 0, cross-check `--mode flip` needs a flip on the last bar, page copy says 'today'. The Live Trading page shows only today's flips; `build_order_ticket.py --all-days` is now moot for AZ.
- **AZ entry window = last 3 trading days (user, 2026-11-23, replaces 'today' above; ND unchanged):** an AZ entry is a Supertrend flip to green within the last 3 trading days that is still green with no open position. `ENTRY_WINDOW_TRADING_DAYS = 3` in the engine, `ENTRY_WINDOW = 3` in `crosscheck_signals.py`, guardrail `entry_window_days` 3 (S3 blocks a flip older than that), `build_order_ticket.py` lists entries up to the window (older only with `--all-days`), page copy says 'last 3 trading days'. Reason: a week of travel should not lose a signal; the backtest showed entry windows 0/1/3/5 are noise (flip-today marginally best), so the change is safe. The backtest label on the dashboard still says flip-today, which is what was tested.
- **Zerodha order lessons (2026-11-14).** (1) Kite rejects a price that is not a multiple of the stock's tick size (POWERINDIA is Rs5.00): read `tick_size` and round the limit DOWN to it. (2) Every Zerodha order also needs Zerodha's own approval: the native form was auto-declined twice, `approval_method: "browser"` returns a link the user approves once; that approval can save 'future orders allowed' so later orders pass on the remembered permission, which never replaces the chat 'yes, place these'. (3) Always pass `exchange`; a holding on BSE (PAGEIND) is a user decision, the NSE SELL was never accepted and the user placed it on BSE in the app (as a LIMIT, not the ticketed MARKET). (4) GTT `place` (two-leg BUY) and `delete` were tested and work; a two-leg ticket with very small premiums and qty 5,200 (BANKINDIA 160CE) was refused with no reason, so small-premium or large-quantity tickets may be rejected; `modify` is untested. (5) `build_gtt_tickets.py` compared a UTC `fetched_at` date with the IST date and refused fresh files between 00:00 and 05:30 IST: fixed. (6) Daily candles pulled the same evening can still carry the last traded price instead of the official close; re-pull after settlement and compare with the published close.
- **Skill tool names (2026-11-14).** The Zerodha connector now exposes grouped tools (`portfolio` / `orders` / `market` / `gtt`) and the Dhan tools may carry either the `mcp__dhan__` or the `mcp__claude_ai_dhan_mcp__` prefix; every refresh/order skill now starts with a note saying the older or alternative names mean the same calls.
- **ONE Dhan order skill (user, 2026-11-16).** `.claude/skills/dhan-order` now runs SIX stages one at a time: dh252 exits, add-ons, entries, then the investment-portfolio shares: share exits (SELL MARKET AMO; `invest_trades.py pending` is recorded before placing), share averaging (BUY LIMIT AMO) and share entries (BUY LIMIT AMO, sized from the previous capital + profit). `dhan-invest-order-entry` and `dhan-invest-order-exit` are deleted (their rules moved into it); the builders are `build_order_ticket.py` (dh252) and `build_share_ticket.py` (shares). Both builders now skip any signal that already has a pending order on the same side (read from `data/orders_snapshot.json`, refreshed at the start of each run), so a signal ordered on an earlier evening is never offered again (`--include-ordered` overrides). If the Dhan quote API is down (`Bad Gateway`), the historical-candle endpoint gives the signal day's O/H/L/C for the limit price. `dhan-superorder` (options) stays separate.

- **Dhan pre-trade funds check: standing override (user, 2026-11-18).** The Dhan MCP `place` pre-trade check fires its sign-flipped "insufficient funds" fault on every order (seen on SELL and BUY, stages 1-2 of 2026-11-18). `/dhan-order` no longer asks for a second yes: after the user's "yes, place these" for the group, a fault-type block (margin check shows funds fine) is retried with `preflight: false` and the one-line note "known fault, override applied". A real shortfall or any other error still stops and is shown verbatim. `dhan-order` only; `dhan-superorder` keeps asking.
