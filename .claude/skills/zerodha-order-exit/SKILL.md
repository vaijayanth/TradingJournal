# zerodha-order-exit - real-money after-market SELL orders for the AZ (Zerodha) exit signals

This skill places REAL orders on the user's Zerodha account through the Zerodha MCP (`mcp__claude_ai_Zerodha_Mcp__*`). Signals are computed after the close and orders go in as AMO (after-market) orders for the NEXT trading day. It is the AZ twin of `dhan-order-exit` and the exit half of `zerodha-order-entry`; ND and AZ share no code or data.

## The AZ exit rule (user, 2026-11-09)
- Exit = Supertrend RED, at any profit or loss, the WHOLE position (no partial exits).
- Grandfathered: a position held at the baseline cut-off (`baseline_from_sheet.json` -> `cutoff_date`, 2026-11-08) only gets an exit signal after a red flip that happens AFTER that date; a position already red at the cut-off stays a hold (the engine decides; this skill never overrides it).
- Only the dashboard's own positions can have an exit signal (the 21 moved from the old sheet plus positions opened through the dashboard). Other Zerodha holdings are not this dashboard's and are never ticketed.

## Scope (hard limits)
- Stocks only. Never options, futures, ETFs, GTTs, BUYs, or any stock without a current exit signal in `zerodha-live/zerodha_live_signals.json` (`exits`), as listed by `python zerodha-live/scripts/build_order_ticket.py exit`. A discretionary or partial sell is out of scope: refuse and say why.
- Quantity = the whole open position, from the builder, which also checks it equals the Zerodha holdings quantity. Never sell more than held.
- AMO MARKET orders, CNC (delivery), exchange NSE (never BSE) - the same rule as ND: when an exit signal exists the position is sold at the next open, whatever the price. No limit price. Never during market hours (step 3). If Zerodha refuses a MARKET order in the AMO window, STOP, show the verbatim error and offer a LIMIT order instead (limit = signal close x 0.98, rounded UP to the 0.05 tick, a price below which you accept not selling); place it only after the user agrees to that exact price.
- One explicit confirmation for the exact batch shown. Any change = show the ticket again and re-confirm. Never act on an implied or earlier "yes".
- Signals flagged by the cross-check (`zerodha-live/data/signal_crosscheck.json`, Supertrend recomputed from complete Yahoo history) are BLOCKED: the builder lists them as BLOCKED and will not ticket them. Never work around it; `--override SYMBOL` exists but only the user may ask for it, naming the stock, after you have shown the reason.
- Never retry a rejected order; never modify or cancel without being asked; never place while a refresh is running.

## Guardrails (hard rules)
- Tickets come ONLY from the ticket builder, which refuses (exit code 2) unless `zerodha-live/data/guardrails.json` is current for the same signals. A GLOBAL block (trading halt, stale data, mass-exit anomaly - 5 or more and 20% of positions flipping red at once is treated as suspect data - NaN, cross-broker import) means nothing may be ordered; per-stock blocks list the stock as BLOCKED. Never work around a block: tell the user the id and message and stop. Only the user can fix the cause or switch off `zerodha-live/data/trading_halt.json`.
- Show every guardrail WARN the builder prints in the ticket, before asking for the "yes".
- Batch caps (`data/guardrails_config.json`: 40 orders, 25% of the capital base per batch); a bigger batch only when the user, after seeing it, explicitly asks for `--allow-big-batch`.
- Kill switch: if the user says stop/halt, set `"halt": true` in `zerodha-live/data/trading_halt.json`; set it back to false only when they say so.
- Re-run `python zerodha-live/scripts/guardrails.py` right before building tickets if more than a few hours have passed since the refresh.

## Steps
1. **Login.** `mcp__claude_ai_Zerodha_Mcp__get_holdings` with `limit: 1`; if it asks to log in, call `login`, show the user the link and wait.
2. **Fresh data, after the close.** The signals must be the day's final ones: the backtester's Daily OHLC Update publishes after the close (16:00, 17:00 and 19:00 IST runs), then `/refresh-zerodha`. The builder refuses data older than 3 days, but you must also check `market_data_date` is the session that just ended, and that `get_holdings` (full, saved to a file) shows each stock's quantity, with no T1 or pledged part blocking the sale: if the available quantity is less than the exit quantity, stop and tell the user.
3. **Market must be closed.** NSE equity trades Mon-Fri 09:15-15:30 IST (plus announced special sessions). If it is open, stop: tell the user to run this after the close. (Weekend/holiday or after 15:30 IST = continue in AMO mode.)
4. **One-shot pick, every time.** Re-run `python zerodha-live/scripts/build_order_ticket.py exit` and print the FULL numbered table again, all rows, even if shown earlier (never "same as before"): number, stock, quantity, reference price, est. proceeds, P&L %, entry date. If the list is empty say "no exit signals". Print every `WARNING` line the builder shows: a **short CALL open on the stock** means selling the shares leaves that call uncovered (naked), so tell the user plainly and suggest closing or hedging the call first (option orders are not part of this skill). Then ask once: "Reply with the numbers to exit - e.g. `1,3` - or `all`." Echo the choice back. Never default to everything. Refuse any stock not in the list.
5. **Tickets.** `python zerodha-live/scripts/build_order_ticket.py exit --pick <numbers>` (same list); read the `TICKETS_JSON=` line (each ticket carries `avg_cost` and `entry_date`) and the printed total.
6. **Reference price (information only).** `get_ltp` or `get_ohlc` with `["NSE:<SYMBOL>", ...]`; after the close `last_price` is the finished session's close (`ohlc.close` is the PREVIOUS close). It is used only for the estimated proceeds. If it differs from the ticket's `ref_price` by more than 3%, say so as a warning; it does NOT stop the order (every exit signal is exited).
7. **No limit price.** The order is a MARKET order: say plainly that the fill price is whatever the market gives at the open, which can be well away from the close on a gap-down. Also say that Zerodha may not accept a market AMO (see Scope) and what you will do then.
8. **Ticket + confirmation.** Table: symbol, SELL, quantity, order type MARKET (AMO), est. proceeds at the close, reason, P&L %, the total, any short-call WARNING, and the line "AFTER-MARKET order for the next trading day - the whole position will be sold at the opening price". Ask the user to reply "yes, place these" and wait. Nothing is placed before that.
9. **Record the average cost BEFORE placing.** For each ticket run `python zerodha-live/scripts/zerodha_trades.py pending --symbol <SYM> --qty <qty> --avg-cost <avg_cost> --date <today IST> --entry-date <entry_date>` using the values in the ticket (never typed by hand). It captures the position's cost while the holdings still have it; the closed trade and its P&L are booked from it.
10. **Place** one at a time with `mcp__claude_ai_Zerodha_Mcp__place_order`: `variety: "amo"`, `exchange: "NSE"`, `tradingsymbol`, `transaction_type: "SELL"`, `quantity`, `product: "CNC"`, `order_type: "MARKET"`, `validity: "DAY"`, `tag: "AZEXIT"`. Place ONE first, check it with `get_orders` (status like `AMO REQ RECEIVED`, no rejection), then place the rest. If the tool reports a validation or window error, STOP and report it verbatim (do not guess other fields); if a pending record was written for an order that was not placed, remove it with `zerodha_trades.py` (`show` first) or tell the user it is harmless until a fill. Stop at the first rejection and say which orders did and did not go through. Never retry.
11. **Verify.** `get_orders`: report order id and status per stock. Nothing has filled yet; never say it has. Rewrite `zerodha-live/data/orders_snapshot.json` with the open AMO orders (`fetched_at`, `source`, `orders[]` with `order_id, symbol, side, qty, order_type, price (null for market), status, amo, placed`) so the Dashboard and Live Trading show them as ordered.
12. **Fills are recorded NEXT trading day.** `/refresh-zerodha` step 4 reads the day's `get_trades`; for every SELL of a position with a `pending_exits` record it runs `zerodha_trades.py fill --symbol <SYM> --qty <qty> --price <average fill price> --date <date>`, which books the closed trade (profit = (exit price - average cost) x quantity, gross of charges) and removes the position from the dashboard. A SELL with no pending record is never guessed: ask the user for the average cost and entry date. Remind the user of this at the end of the placement. An exit that did not fill stays pending; say so.

## Reporting
Plain: placed (as AMO) / status / still pending / failed (verbatim error). Never call a pending AMO filled.
