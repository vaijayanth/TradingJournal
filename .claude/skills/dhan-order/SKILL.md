# dhan-order - real-money after-market orders for the Dhan (dh252) signals, one group at a time

This skill places REAL orders on the user's Dhan account through the Dhan MCP (`mcp__claude_ai_dhan_mcp__*`). Signals are computed after the close and orders go in as AMO (after-market) orders for the NEXT trading day. It works in three **stages, in this order**: **1) EXITS** (SELL), **2) ADD-ONS** (BUY), **3) ENTRIES** (BUY). Each stage is listed, the user may exclude stocks, the user confirms, the orders are placed and VERIFIED, and only then does the next stage start. It replaces `dhan-order-entry` and `dhan-order-exit` and is the ND twin of `zerodha-order`; ND and AZ share no code or data. The investment-portfolio shares have their own skills (`dhan-invest-order-entry` / `dhan-invest-order-exit`); option super orders are `dhan-superorder`.

## The dh252 rules these orders come from
- Entry: 52-week high (closing high) + Supertrend green, not held; size = the effective tier (base Rs1,000, +tiers, doubling milestone), floored to whole shares, minimum 1 (a stock priced above the tier costs more than the tier). Add-on: P&L at -6% or worse, 1/10 of the open quantity (minimum 1), once every 7 days. Exit: Supertrend RED, the whole position, any profit or loss. Fixed capital base Rs20,00,000. All of it is computed by the engine; this skill never recomputes or overrides it.

## Scope (hard limits)
- Stocks only. Never options, futures, ETFs, the option-hedge / investment portfolio, or a stock the engine does not list. A discretionary or partial sell is out of scope: refuse and say why.
- Only symbols in the current signal file (`dhan-live/dhan_live_signals.json`) as `exits`, `addons` or `entries`, exactly as listed by `python dhan-live/scripts/build_order_ticket.py <exit|addon|entry>`. Quantities come from that script, never from the user or you (an exit sells the whole position; the script checks it equals the Dhan holdings quantity). A stock with no signal is refused.
- **BUYs (add-ons, entries):** AMO LIMIT, CNC. **SELLs (exits):** AMO MARKET, CNC: when an exit signal exists the position is sold at the next open whatever the price (the user's rule; no price guard blocks it). Never a market BUY. Never during market hours (step 3).
- **One group at a time.** Never list, ticket or place the next group before the current group is placed AND verified (or the user says to skip it). Never combine groups in one confirmation.
- One explicit confirmation per group, for the exact batch shown. Any change (stock, quantity, price) = show the ticket again and re-confirm. Never act on an implied or earlier "yes".
- Signals flagged by the cross-check (`dhan-live/data/signal_crosscheck.json`, recomputed from complete Yahoo history) are BLOCKED: the builder lists them and will not ticket them. Never work around it; `--override SYMBOL` exists but only the user may ask for it, naming the stock, after you have shown the reason.
- Never retry a rejected/failed order; never modify or cancel without being asked; never place while a refresh is running.

## Guardrails (hard rules)
- Tickets come ONLY from the builder, which refuses (exit code 2) unless `dhan-live/data/guardrails.json` is current for the same signals. A GLOBAL block (trading halt, stale data, a mass-exit anomaly - 5 or more and 20% of positions flipping red at once is treated as suspect data - NaN, cross-broker import, the F5 price cross-check failing on 25% or more of signals) means nothing may be ordered; per-stock blocks (bad P&L, wrong quantity vs holdings, bought-but-unsettled, oversell ...) list the stock as BLOCKED. Never work around a block: tell the user the id and message and stop. Only the user can fix the cause or switch off `dhan-live/data/trading_halt.json`.
- Show every guardrail WARN the builder prints in each stage's ticket, before asking for the "yes".
- Batch caps (`data/guardrails_config.json`: 40 orders, 25% of the capital base per batch); a bigger batch only when the user, after seeing it, explicitly asks for `--allow-big-batch`.
- Kill switch: if the user says stop/halt, set `"halt": true` in `dhan-live/data/trading_halt.json`; set it back to false only when they say so.
- Re-run `python dhan-live/scripts/guardrails.py` right before building tickets if more than a few hours have passed since the refresh.

## Before the stages (once per run)
1. **Login.** `mcp__claude_ai_dhan_mcp__portfolio_agent_tool` action `holdings`; if it says not logged in, call the MCP `login` tool, give the user the link and wait.
2. **Fresh data, after the close.** The signals must be the day's final ones: the backtester's Daily OHLC Update publishes after the close (16:00, 17:00 and 19:00 IST runs), then `/refresh-dhan`. The builder refuses data older than 3 days, but you must also check `market_data_date` is the session that just ended.
3. **Market must be closed.** NSE equity trades Mon-Fri 09:15-15:30 IST (plus announced special sessions). If it is open, stop. (Weekend/holiday or after 15:30 IST = continue in AMO mode.)
4. **Overview.** Run `python dhan-live/scripts/build_order_ticket.py all` once and tell the user in one line how many rows each group has (exits / add-ons / entries) and that you will take them one group at a time in that order. Groups with 0 rows are named in that line too ("no exits, no add-ons today"), but each empty group is still announced and acknowledged in its own turn (see the loop). This is only a count, not a pick list.

## The loop - repeat for each group in order: EXITS, then ADD-ONS, then ENTRIES
**A0. Empty group.** If the builder shows 0 rows for this group, do NOT silently skip it. Say explicitly, in its own message, "No <exit signals / add-on signals / entry signals> today for this group" (and, if it applies, why in one line: for example entries hidden by the cross-check, or older flips hidden by the freshest-day rule), then ask exactly: "Move ahead to <next group>?" and WAIT for the user's yes before listing the next group. For the last group (entries) there is no next group: say there are no entries and that the run is finished. A "skip" or "no" answer ends the run. Never place anything in an empty group.

**A. List.** Re-run the builder for ONLY this group (`... build_order_ticket.py exit`, then `addon`, then `entry`) and print the FULL numbered table (numbers restart at 1 in each group), all rows, even if shown earlier (never "same as before"): number, stock, quantity, reference price, est. value, reason (exits: P&L %, flip; add-ons: P&L % and days since the last buy; entries: 52-week high and flip). Print every builder guardrail WARN and BLOCKED line.
- **EXITS only:** confirm with `portfolio_agent_tool` `holdings` that each stock's available quantity (`avail`, not T1 or pledged) covers the sale; if it is less, tell the user and drop that stock.
- **BUY groups:** directly under the table show a **capital check**: from `portfolio_agent_tool` action `funds` the Dhan available balance (cash + collateral margin), withdrawable cash, collateral and utilised; from `dhan_live_signals.json` the dh252 base (Rs20,00,000 fixed), dh252 invested now (sum of the open positions) and the undeployed remainder; this group's est. value (+2% worst case) as a % of available balance, of withdrawable cash and of the base, and, from stage 3 on, what the earlier groups already used. Say plainly that most of the available balance is collateral, not cash. Never count exit proceeds as available funds.

**B. Ask, with exclusions.** Ask exactly one question: "Go ahead with all N, or tell me which to exclude (e.g. `exclude 2,4` or a stock name)? Say `skip` to skip this group." Translate the reply into the pick (all minus the exclusions) and echo the final list back. Never default silently; if the reply is unclear, ask again. An excluded stock is simply not ordered (it stays a signal; say so). The user may also name stocks, which must come from this same group's list; refuse any stock not in it.

**C. Ticket.** `python dhan-live/scripts/build_order_ticket.py <group> --pick <numbers>`; read the `TICKETS_JSON=` line and the printed total.

**D. Prices and funds.** For each ticket get the NSE EQUITY `securityId` with `search_agent_tool` action `search`, payload `{"query": "<SYMBOL>-EQ"}` (the `NSE E ... EQUITY` row; the BSE row is not used), then ONE `market_data_agent_tool` action `ohlc` call `{"NSE_EQ": [<ids>]}` (after the close it returns the finished session as `O/H/L/C`). If a close differs from the ticket's `ref_price` by more than 3%: for BUYs stop and ask; for exits show it as a warning only (every exit signal is exited).
- **BUYs:** limit = min(session high, close x 1.02), the cap rounded DOWN to the 0.05 tick. Show close, high, cap and limit side by side and mark rows where the cap applied; say plainly that a limit order fills at the open when the stock opens at or below it (you normally pay the opening price), on a gap-up it can fill up to the limit, and above the limit it does not fill. The user may override a price. Funds: `margin_agent_tool` action `single` (NOT `multi`, which returned 0) per order, payload `{"exchangeSegment":"NSE_EQ","transactionType":"BUY","quantity":<q>,"productType":"CNC","securityId":"<id>","price":<limit>}`; compare Total Margin with Available Balance for the group (its "Insufficient Balance" line is nonsense - ignore it). A batch of many small orders may be checked on the largest order plus the full-value sum. Stop and tell the user if funds are short.
- **EXITS:** MARKET, no price: say plainly that the fill is whatever the market gives at the open, which can be well away from the close on a gap-down.

**E. Confirm.** Show the ticket table for this group (exits: symbol, SELL, quantity, MARKET AMO, est. proceeds at the close, reason, P&L %; BUYs: symbol, quantity, limit, value at the limit, reason), the total next to available balance / withdrawable cash and the dh252 base, every guardrail WARN, and the line "AFTER-MARKET orders for the next trading day". Ask the user to reply "yes, place these" and wait. Nothing is placed before that.

**F. Place** one at a time with `trading_agent_tool` action `place`:
- EXIT: `{"exchangeSegment":"NSE_EQ","transactionType":"SELL","quantity":<q>,"productType":"CNC","securityId":"<id>","price":0,"orderType":"MARKET","validity":"DAY","afterMarketOrder":true,"amoTime":"OPEN"}`.
- ADD-ON / ENTRY: `{"exchangeSegment":"NSE_EQ","transactionType":"BUY","quantity":<q>,"productType":"CNC","securityId":"<id>","price":<limit>,"orderType":"LIMIT","validity":"DAY","afterMarketOrder":true,"amoTime":"OPEN"}` (Dhan's AMO options are PRE_OPEN / OPEN / OPEN_30 / OPEN_60; OPEN unless the user says otherwise).
The tool's own pre-trade funds check is BROKEN (it rejects with a sign-flipped "shortfall" even when the balance is far above the order). If `place` is blocked as "insufficient funds" and the margin check showed the funds are fine, STOP, show the user the message once, explain it is that known fault, and only after the user's explicit yes add `"preflight": false` to that order and the rest of the group. On any other validation error STOP and report it verbatim; do not guess other fields. Place ONE first, check it with `orderbook_agent_tool` action `list` (PENDING, no error), then place the rest of the group. Stop at the first rejection, say which orders did and did not go through, and do NOT start the next group until the user says how to proceed. Never retry.

**G. Verify (this is the gate to the next group).** `orderbook_agent_tool` action `list`: for EVERY order of this group confirm it is present with the expected side, quantity, price and a PENDING (accepted) status, not rejected or cancelled. Report order id and status per stock in a table. Nothing has filled yet; never say it has. Rewrite `dhan-live/data/orders_snapshot.json` with the orders still PENDING (`fetched_at`, `source`, `orders[]` with `order_id, symbol, side, qty, order_type, price (null for market), status, amo`), keeping any other pending orders already in it. Then say plainly "<group> done and verified: N of N accepted" and only THEN go to the next group (back to A0/A). If anything is missing or rejected, stop and report; do not continue.

## After the last group
Summarise per group: placed / verified / skipped / excluded / failed (verbatim error). Remind the user: the Dhan tradebook is TODAY-ONLY, so on the next trading day (after the open) `/refresh-dhan` must run: its tradebook step records the fills with `append_fills.py` (quantities come from the order book, since the tradebook reports 0), and a filled exit becomes a closed trade. Orders that did not fill (limit not reached) stay out of the trade log; say so. A missed day loses the fills.

## Reporting
Plain: placed (as AMO) / status / still pending / failed (verbatim error). Never call a pending AMO filled.
