# zerodha-order - real-money after-market orders for the AZ (Zerodha) signals, one group at a time

This skill places REAL orders on the user's Zerodha account through the Zerodha MCP (`mcp__claude_ai_Zerodha_Mcp__*`). Signals are computed after the close and orders go in as AMO (after-market) orders for the NEXT trading day. It works in three **stages, in this order**: **1) EXITS** (SELL), **2) ADD-ONS** (BUY), **3) ENTRIES** (BUY). Each stage is listed, the user may exclude stocks, the user confirms, the orders are placed and VERIFIED, and only then does the next stage start. It is the AZ twin of `dhan-order`; ND and AZ share no code or data. Option GTTs are `zerodha-gtt-order`, not this skill.

## The AZ rules these orders come from (user, 2026-11-09)
- Universe: Nifty F&O stocks (`zerodha-live/data/fno_universe.json`), minus `excluded_symbols.json` (BSE, BEL, RECLTD). Only the dashboard's own positions (the 21 moved from the old sheet plus positions opened through it) can have exit or add-on signals; other Zerodha holdings are never ticketed.
- **EXIT:** Supertrend RED, any profit or loss, the WHOLE position (never partial). Grandfathered: a position already red at the baseline cut-off (2026-11-08) only gets an exit signal after a red flip AFTER that date; the engine decides, this skill never overrides it.
- **ADD-ON:** a tracked position with Supertrend green and P&L at -6% or worse (same as ND): buy 1/10 of the quantity (minimum 1), once every 7 days. Not a flip signal, so always listed.
- **ENTRY:** Supertrend flipped to green within the last 3 trading days and NO holding in that stock anywhere in the account. Size = Rs20,000 (+Rs5,000 per 100 trades, open + closed), floored to whole shares, minimum 1 (a stock priced above the tier costs more than the tier). **Only the freshest flip day is listed** (today's flips if any are orderable, else yesterday's, then 2 and 3 days ago); older flips are hidden (`--all-days` shows them, only when the user asks). A blocked signal does not count as orderable.
- Fixed capital base Rs30,00,000.

## Scope (hard limits)
- Stocks only. Never options, futures, ETFs, GTTs, or an excluded symbol. A discretionary or partial sell is out of scope: refuse and say why.
- Only symbols in the current signal file (`zerodha-live/zerodha_live_signals.json`) as `exits`, `addons` or `entries`, exactly as listed by `python zerodha-live/scripts/build_order_ticket.py <exit|addon|entry>`. Quantities come from that script, never from the user or you (an exit sells the whole position; the script checks it equals the holdings quantity). A stock with no signal is refused.
- **BUYs (add-ons, entries):** AMO LIMIT, CNC, NSE (never BSE). **SELLs (exits):** AMO MARKET, CNC, NSE: when an exit signal exists the position is sold at the next open whatever the price (the ND rule). If Zerodha refuses a MARKET order in the AMO window, STOP, show the verbatim error and offer a LIMIT instead (limit = signal close x 0.98, rounded UP to the 0.05 tick); place it only after the user agrees to that exact price. Never a market BUY. Never during market hours (step 3).
- **One group at a time.** Never list, ticket or place the next group before the current group is placed AND verified (or the user says to skip it). Never combine groups in one confirmation.
- One explicit confirmation per group, for the exact batch shown. Any change (stock, quantity, price) = show the ticket again and re-confirm. Never act on an implied or earlier "yes".
- Signals flagged by the cross-check (`zerodha-live/data/signal_crosscheck.json`, Supertrend recomputed from complete Yahoo history) are BLOCKED: the builder lists them and will not ticket them. Never work around it; `--override SYMBOL` exists but only the user may ask for it, naming the stock, after you have shown the reason.
- Never retry a rejected order; never modify or cancel without being asked; never place while a refresh is running.

## Guardrails (hard rules)
- Tickets come ONLY from the builder, which refuses (exit code 2) unless `zerodha-live/data/guardrails.json` is current for the same signals. A GLOBAL block (trading halt, stale data, a mass-exit anomaly - 5 or more and 20% of positions flipping red at once is treated as suspect data - NaN, cross-broker import) means nothing may be ordered; per-stock blocks list the stock as BLOCKED. Never work around a block: tell the user the id and message and stop. Only the user can fix the cause or switch off `zerodha-live/data/trading_halt.json`.
- Show every guardrail WARN the builder prints in each stage's ticket, before asking for the "yes".
- Batch caps (`data/guardrails_config.json`: 40 orders, 25% of the capital base per batch); a bigger batch only when the user, after seeing it, explicitly asks for `--allow-big-batch`.
- Kill switch: if the user says stop/halt, set `"halt": true` in `zerodha-live/data/trading_halt.json`; set it back to false only when they say so.
- Re-run `python zerodha-live/scripts/guardrails.py` right before building tickets if more than a few hours have passed since the refresh.

## Before the stages (once per run)
1. **Login.** `mcp__claude_ai_Zerodha_Mcp__get_margins`; if it asks to log in, call `login`, show the link and wait.
2. **Fresh data, after the close.** The signals must be the day's final ones: the backtester's Daily OHLC Update publishes after the close (16:00, 17:00 and 19:00 IST runs), then `/refresh-zerodha`. The builder refuses data older than 3 days, but you must also check `market_data_date` is the session that just ended.
3. **Market must be closed.** NSE equity trades Mon-Fri 09:15-15:30 IST (plus announced special sessions). If it is open, stop. (Weekend/holiday or after 15:30 IST = continue in AMO mode.)
4. **Overview.** Run `python zerodha-live/scripts/build_order_ticket.py all` once and tell the user in one line how many rows each group has (exits / add-ons / entries) and that you will take them one group at a time in that order. Groups with 0 rows are named in that line too ("no exits, no add-ons today"), but each empty group is still announced and acknowledged in its own turn (see the loop). This is only a count, not a pick list.

## The loop - repeat for each group in order: EXITS, then ADD-ONS, then ENTRIES
**A0. Empty group.** If the builder shows 0 rows for this group, do NOT silently skip it. Say explicitly, in its own message, "No <exit signals / add-on signals / entry signals> today for this group" (and, if it applies, why in one line: for example entries hidden by the cross-check, or older flips hidden by the freshest-day rule), then ask exactly: "Move ahead to <next group>?" and WAIT for the user's yes before listing the next group. For the last group (entries) there is no next group: say there are no entries and that the run is finished. A "skip" or "no" answer ends the run. Never place anything in an empty group.

**A. List.** Re-run the builder for ONLY this group (`... build_order_ticket.py exit`, then `addon`, then `entry`) and print the FULL numbered table (numbers restart at 1 in each group), all rows, even if shown earlier (never "same as before"): number, stock, quantity, reference price, est. value, reason (for exits: P&L %, entry date; for add-ons: P&L % and days since the last buy; for entries: flip date). Print every builder `WARNING` and BLOCKED line.
- **EXITS only:** a **short CALL open on an exit stock** means selling the shares leaves that call uncovered (naked): say so plainly and suggest closing or hedging the call first (option orders are not part of this skill). Also confirm with the full `get_holdings` (saved to a file) that the available quantity covers each sale (no T1 or pledged part blocking it); if not, tell the user and drop that stock.
- **BUY groups:** directly under the table show a **capital check** from `get_margins` (equity available cash, collateral, utilised) and `zerodha_live_signals.json` (`capital_base`, invested now, undeployed): this group's est. value (+2% worst case) as a % of available cash and of the Rs30,00,000 base, and, from stage 3 on, what the earlier groups already used. Say plainly how much of the balance is collateral rather than cash. Never count exit proceeds as available funds.

**B. Ask, with exclusions.** Ask exactly one question: "Go ahead with all N, or tell me which to exclude (e.g. `exclude 2,4` or a stock name)? Say `skip` to skip this group." Translate the reply into the pick (all minus the exclusions) and echo the final list back. Never default silently; if the reply is unclear, ask again. An excluded stock is simply not ordered (it stays a signal; say so). The user may also name stocks to ADD only from this same group's list; refuse any stock not in the list.

**C. Ticket.** `python zerodha-live/scripts/build_order_ticket.py <group> --pick <numbers>`; read the `TICKETS_JSON=` line (exit tickets carry `avg_cost` and `entry_date`) and the total.

**D. Prices.** `get_ohlc` with `["NSE:<SYMBOL>", ...]` for the group (one call). NOTE: Zerodha's `ohlc.close` is the PREVIOUS session's close; after the close the finished session's close is `last_price`, and `ohlc.high` is the session high. Use `last_price` as the close. If a close differs from the ticket's `ref_price` by more than 3%: for BUYs stop and ask; for exits show it as a warning only (every exit signal is exited).
- **BUYs:** limit = min(session high, close x 1.02), the cap rounded DOWN to the 0.05 tick (if the exchange rejects a price for tick size, report it verbatim and show the corrected price for a fresh yes; never guess). Show close, high, cap and limit side by side, mark rows where the cap applied; say plainly that a limit order fills at the open when the stock opens at or below it (you normally pay the opening price), on a gap-up it can fill up to the limit, and above the limit it does not fill. The user may override a price. Funds: compare the group's total at the limits with `get_margins` equity available cash (delivery needs the full value; collateral counts only partly for a CNC buy). Stop and tell the user if cash is short.
- **EXITS:** MARKET, no price: say plainly the fill is whatever the market gives at the open, which can be well away from the close on a gap-down, and that Zerodha may refuse a market AMO (see Scope).

**E. Confirm.** Show the ticket table for this group (exits: symbol, quantity, MARKET AMO, est. proceeds, reason, P&L %, any short-call WARNING; BUYs: symbol, quantity, limit, value at the limit, reason), the total next to available cash / the capital base, and the line "AFTER-MARKET orders for the next trading day". Ask the user to reply "yes, place these" and wait. Nothing is placed before that.

**F. Record cost (EXITS only), then place.** For each exit ticket first run `python zerodha-live/scripts/zerodha_trades.py pending --symbol <SYM> --qty <qty> --avg-cost <avg_cost> --date <today IST> --entry-date <entry_date>` with the values in the ticket (never typed by hand): it captures the cost while the holdings still have it; the closed trade and its P&L are booked from it. Then place one at a time with `mcp__claude_ai_Zerodha_Mcp__place_order`, `variety: "amo"`, `exchange: "NSE"`, `product: "CNC"`, `validity: "DAY"`:
- EXIT: `transaction_type: "SELL"`, `order_type: "MARKET"`, `tag: "AZEXIT"`.
- ADD-ON: `transaction_type: "BUY"`, `order_type: "LIMIT"`, `price: <limit>`, `tag: "AZADD"`.
- ENTRY: `transaction_type: "BUY"`, `order_type: "LIMIT"`, `price: <limit>`, `tag: "AZENTRY"`.
Place ONE first and check it with `get_orders` (status like `AMO REQ RECEIVED`, no rejection), then place the rest of the group. On a validation or window error STOP, report it verbatim and do not guess other fields; if an exit's pending record was written for an order that was not placed, tell the user it is harmless until a fill (or remove it with `zerodha_trades.py`). Stop at the first rejection, say which orders did and did not go through, and do NOT start the next group until the user says how to proceed. Never retry.

**G. Verify (this is the gate to the next group).** `get_orders` (large; saved to a file): for EVERY order of this group confirm it is present with the expected side, quantity, order type, price and tag and an accepted status (not rejected, not cancelled). Report order id and status per stock in a table. Nothing has filled yet; never say it has. Rewrite `zerodha-live/data/orders_snapshot.json` with the open AMO orders (`fetched_at`, `source`, `orders[]` with `order_id, symbol, side, qty, order_type, price (null for market), status, amo, placed`); orders the user placed themselves (for example for the old sheet dashboard) stay in it, untouched; the AZ pages hide orders for stocks that are not part of this dashboard. Then say plainly "<group> done and verified: N of N accepted" and only THEN go to the next group (back to A0/A). If anything is missing or rejected, stop and report; do not continue.

## After the last group
Summarise per group: placed / verified / skipped / excluded / failed (verbatim error). Remind the user: fills are recorded NEXT trading day by `/refresh-zerodha` step 4, which reads the day's `get_trades`: every BUY of an F&O stock runs `zerodha_trades.py buy --symbol <SYM> --date <date>` (with `--entry` when the stock was not held before; this starts the weekly add cooldown), and every SELL of a position with a `pending_exits` record runs `zerodha_trades.py fill --symbol <SYM> --qty <qty> --price <average fill price> --date <date>`, booking the closed trade (profit = (exit - average cost) x quantity, gross of charges). A SELL with no pending record is never guessed: ask for the average cost and entry date. Orders that did not fill (limit not reached) are not recorded; say so.

## Reporting
Plain: placed (as AMO) / status / still pending / failed (verbatim error). Never call a pending AMO filled.
