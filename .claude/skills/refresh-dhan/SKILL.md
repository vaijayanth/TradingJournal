# Refresh Dhan (dh252)

Run from the repo root of TradingJournal on branch `claude/beautiful-hamilton-fwa55n`. Needs Python 3.10+ with pandas + yfinance, and the Dhan MCP connector (claude.ai account). Everything lives under `dhan-live/`.

## Steps

1. **Prep.** `git status`, `git pull --ff-only` on the branch. Stop and tell the user if the tree has unrelated uncommitted changes.
2. **Dhan login check.** Call `mcp__claude_ai_dhan_mcp__portfolio_agent_tool` (action `holdings`). If it reports not logged in / expired, call the MCP `login` tool, give the user the link, wait for them to approve (`complete_login` if it asks for a code - never ask the user to paste tokens into chat beyond what that flow requires).
3. **Holdings.** Write the result to `dhan-live/data/holdings_snapshot.json` as
   `{"fetched_at": <ISO now, +05:30>, "source": "mcp__claude_ai_dhan_mcp__portfolio_agent_tool (holdings)", "holdings": [{"symbol","qty","avg_cost","invested"}, ...]}`. Keep ALL holdings (the hedge portfolio is filtered by the engine).
4. **Today's fills.** `mcp__claude_ai_dhan_mcp__tradebook_agent_tool` action `list`. The MCP returns **today's trades only**, so this must run every trading day or fills are lost. If there are equity trades, build a JSON list `[{"symbol","date":"YYYY-MM-DD","action":"BUY|SELL","qty","price","order_id"}]` in the scratchpad (equity only - drop any option/F&O rows) and run
   `python dhan-live/scripts/append_fills.py <that file>`.
   **If days were missed (standing rule, user 2026-11-12): do option B FIRST, without asking.** Rebuild the missing fills from the holdings diff: for every non-hedge, non-out-of-scope symbol where holdings qty differs from the fills ledger (sum of BUY minus SELL), record the difference as a BUY (qty up) or SELL (qty down) at the holdings avg cost (a pure new position: its avg cost is the fill price; for a changed position derive the price from the avg-cost change, and if that is not exact say so), dated the first session after the last refresh (use the pending-order dates in `orders_snapshot.json` to pick the day); build the list in the scratchpad and run `append_fills.py`. Skip pending orders that are not in holdings (they did not fill). State in the report that the fills were reconstructed from holdings (assumes no other trades), then offer the CSV as the exact alternative. Only if the diff is not a clean pure-BUY/SELL (e.g. a partial sell of a position with an unknown price) fall back to asking for the CSV.
   Exact route: ask the user for a Dhan *Global Transaction Report* CSV and run
   `python dhan-live/scripts/import_dhan_transactions.py --csv <csv> --holdings dhan-live/data/holdings_snapshot.json --trade-log dhan-live/data/dh252_trade_log.json` (full replace of fills; equity only, excludes the investment/option-hedge portfolio and pre-21-Oct-2026 sells). It stops and lists unresolved names - add them to `data/dhan_name_map.json`, never guess.
4a. **Share averaging record.** From the same tradebook output, for any BUY of a Covered Call universe stock (keys of `dhan-live/data/cc_config.json` -> `universe`: MCX, SHRIRAMFIN, CGPOWER, BSE, DIXON, HCLTECH, INFY, BANKINDIA, BPCL, CUMMINSIND) set `last_add[SYMBOL] = <trade date>` in `dhan-live/data/cc_adds.json`. The averaging rule (green Supertrend, loss >= 6%, 1/10 of open qty, once every 7 days) uses this; the MCP tradebook is today-only, so a missed day means a missed add. If the user says they averaged a stock earlier, record that date too.
4a2. **Investment-share SELL fills.** For any SELL of a Covered Call universe stock in the same tradebook output, check `dhan-live/data/invest_trades.json` `pending_exits` for that symbol (written by `dhan-invest-order-exit` when the order was placed). If one exists and the SELL fully filled, compute the average fill price and run `python dhan-live/scripts/invest_trades.py fill --symbol <SYM> --qty <qty> --price <avg fill price> --date <fill date>`; this books the profit (gross of charges) that sizes the next entry. If a universe SELL has no pending record, do NOT guess its capital: tell the user and ask for the position's average cost before recording. If a pending exit did not fill, leave it and say so.
4a3. **Order snapshot.** `mcp__claude_ai_dhan_mcp__orderbook_agent_tool` action `list`; rewrite `dhan-live/data/orders_snapshot.json` (`fetched_at`, `source`, and `orders[]` with `order_id, symbol, side, qty, order_type, price (null for market), status, amo`) with the orders still PENDING; drop orders that filled, were rejected or lapsed. The Dashboard and Live Trading read this file for the "Ordered / Not ordered" status; if it is stale the page shows old status.
4b. **Covered Call page inputs.** (a) `mcp__claude_ai_dhan_mcp__portfolio_agent_tool` action `positions` -> save the raw text result **verbatim** to `dhan-live/data/cc_raw/positions.txt` (overwrite). Option positions are never copied anywhere else. (b) Chains are fetched in step 5b only for stocks that need a suggestion.
4b2. **Super order scan.** Call `mcp__claude_ai_dhan_mcp__orderbook_agent_tool` action `super_list`, save the raw text verbatim to `dhan-live/data/cc_raw/super_orders.txt`, then run `python dhan-live/scripts/scan_super_orders.py` (needs today's `cc_raw/positions.txt` from step 4b). It flags orphaned stop legs (a stop that could BUY a new long), shorts with no stop, off-rule stops and quantity mismatches; they show as 'Invalid stop order' / 'No stop placed' alerts and guardrail P5. Report the count and the HIGH ones in the verify step; cancelling them is the `dhan-superorder` skill, only when the user asks.
4c. **Live prices (MANDATORY every refresh).** Call `mcp__claude_ai_dhan_mcp__market_data_agent_tool` action `ltp` with `{"NSE_EQ": [<security_id of every stock in dhan-live/data/cc_config.json universe>]}`, save the raw text to a scratch file and run `python dhan-live/scripts/cc_prices.py <file>` (it prints MISSING if an id returned nothing). The Covered Call engine uses these (same IST day only) for near/breached strike alerts and leg distances; without them the alerts use the last close and can be hours or a day wrong. Always say in the report whether live prices were pulled and at what time.
5. **Rebuild.** `python dhan-live/scripts/refresh_dhan.py` (fetches backtester screens, derives entry signals, rebuilds yfinance closes + SMA50/200, regenerates `dhan_live_signals.json`).
5b. **Option chains (only if the run printed `CHAINS NEEDED`).** For each listed symbol call `mcp__claude_ai_dhan_mcp__market_data_agent_tool` action `optionchain` with payload `{"UnderlyingScrip": <security_id>, "UnderlyingSeg": "NSE_EQ", "Expiry": "<expiry>"}` and save the raw text to `dhan-live/data/cc_raw/chains/<SYMBOL>_<EXPIRY>.txt` (delete older chain files first; rows that are all zeros may be omitted, nothing else edited). Then `python dhan-live/scripts/refresh_dhan.py --cc-only`. Expiry dates come from `expirylist` (update `expiries` in `data/cc_config.json` when a new series appears). Lot sizes in `cc_config.json` come from open positions; if a stock has `lot: null`, say so rather than guessing.
5c00. **Standing price policy (user, 2026-11-13).** Yahoo stays the history source. Dhan supplies the latest candles for every signal stock (step 5c0). Dhan's tool returns only a summary and the last 5 candles WITHOUT dates (no full-history option), so there is no Dhan full-year tiebreaker: a stock still flagged afterwards is reported as flagged and stays blocked, unless the user explicitly overrides it by name. TradingView (unadjusted) is the reference convention, so a gap that comes only from dividend adjustment (for example a stock the backtester shows at a 52-week high but whose unadjusted closing high is higher) is a correct flag.
5c000. **Dhan's daily history lags one session (found 2026-11-13).** After the close, `historical` still ends at the PREVIOUS session (it has no candle for today until the next day), so matching its latest close to the signal close fails for every stock and must NOT be read as stale signals. For the signal day use `historical_data_agent_tool` action `intraday` instead: `{"securityId","exchangeSegment":"NSE_EQ","instrument":"EQUITY","interval":"60","oi":false,"fromDate":"<day> 09:15:00","toDate":"<day> 15:30:00"}`; its summary gives the day's open, high, low and the last-trade close. The last trade is not NSE's official close (the official close is a 30-minute average), so compare it to the published close with a 2% tolerance and report any stock beyond it; a stock with no intraday data (it did not trade) cannot be checked and stays flagged. Use this check; do not write intraday bars into the overlay (their close differs from the official close and would raise false flags).
5c0. **Dhan is the final price source (user, 2026-11-13).** On EVERY refresh pull Dhan's last candles for every stock with an entry/add-on/exit signal (not only flagged ones): `historical_data_agent_tool` `historical` needs the NUMERIC securityId from `data/dhan_security_ids.json` (the symbol is rejected; look up missing ids with `search_agent_tool` query `<SYMBOL>-EQ`), window = the last session date minus 2 days to today+1. The tool returns only a summary and the last 5 candles WITHOUT dates (it cannot return full history), so date them by matching the latest candle's close to the published signal close; write them to `data/dhan_bars_overlay.json`. A Dhan bar REPLACES Yahoo's bar for that date. If Dhan's latest close differs from the published close, the signal is stale and stays blocked. Then continue with 5c below.
5c. **Dhan bar overlay (when the cross-check flags date-lag, user 2026-11-12).** If `data/signal_crosscheck.json` flags signals only because "last bar is <date> (Yahoo), signals are dated <later>" (Yahoo publishes small-cap closes late), fill the gap from Dhan: for each such symbol take its securityId from `dhan-live/data/dhan_security_ids.json` (if missing, `mcp__dhan_mcp__search_agent_tool` query=<SYMBOL> exchange NSE, take the `-EQ` NSE_EQ id and add it to that file), call `mcp__dhan_mcp__historical_data_agent_tool` action `historical` with `{"securityId","exchangeSegment":"NSE_EQ","instrument":"EQUITY","expiryCode":0,"oi":false,"fromDate":<last Yahoo bar date>,"toDate":<today+1>}`, and write the missing session candles (O/H/L/C/V; the last candle is the latest session, a stock with no trade that day returns no candle) into `dhan-live/data/dhan_bars_overlay.json` (`bars: {SYMBOL: [{date, open, high, low, close, volume}]}`, replace the file). Then re-run `python dhan-live/scripts/refresh_dhan.py`. `crosscheck_signals.py` appends these only AFTER Yahoo's last bar and never past the signals' market_data_date, so Yahoo is never overwritten. A flag that remains afterwards (a close that differs from the published one, below the closing high) is a REAL disagreement: report it, do not paper over it. Never use the overlay to clear a flag you have not checked against the Dhan candle.
6. **Verify before committing - report these to the user:**
   - The engine prints no `WARNING` (a drift warning means fills and holdings disagree: a missed fill, or a position that exited outside tracking).
   - Open positions in scope == holdings qty/WAC for every dh252 symbol (the engine's 48-style count; any `exited_outside_tracking` list must be empty or explained).
   - Market data date and SMA as-of date are the latest trading day (not older than the previous session).
   - Signal cross-check (`data/signal_crosscheck.json`, printed by the refresh): list every FLAG with its reason. Flags mean the published signal disagrees with a recompute on complete Yahoo history (stale/holey backtester prices, a different closing high, or a missing bar) - such signals are blocked from orders. If many flags appear at once, suspect the backtester's price history (missing bars) before blaming the stocks.
   - Counts: exits / add-ons / entries / closed trades / realised + unrealised P&L. Flag anything surprising (an add-on with P&L > -6%, an exit that isn't Supertrend red, etc. means a bug - investigate, don't publish).
   - Covered Call: report the Options alerts (EXIT / WARN / ENTER) and the Shares tab signals (entry signals, averaging due), that the options MTM ties to Dhan's "Unrealized P&L" in the positions output, and which stocks still have no chain or lot size. Deltas are Black-Scholes estimates from the chain's IV (no dividends) - say so.
6c. **Action board (always, after the verify step).** Present ONE compact table per group with short phrases, built from the data just refreshed (read-only; place nothing):
   - **dh252 stocks:** `python dhan-live/scripts/build_order_ticket.py all` (counts) and the exit / add-on / entry lists from `build_order_ticket.py exit|addon|entry` (today's entries only). Orderable vs blocked (cross-check / guardrail) shown separately with the reason.
   - **Investment shares:** `python dhan-live/scripts/build_share_ticket.py exit` and `entry` and `add` (exit = red and in profit; entry = fresh flip; averaging due, with the stocks still in cooldown and their due date).
   - **Options:** from `covered_call_signals.json` alerts: Exit (colour flipped), 3x premium, Event close, Profit Exit, plus the super-order scan (orphan stops = HIGH, shorts with no stop). One row per leg with Issue and Action in the page's short wording.
   - **Clean-up row (always shown, even when empty):** list exactly what would be cancelled or fixed, one line each with the order id and the reason, from `data/super_scan.json`: orphaned stop/target legs (S1: stop that could BUY a new long, HIGH; a target leg left PENDING after its stop fired), wrong-level or wrong-quantity stops (S3, S4), and any stop leg whose option has EXPIRED (expiry before today) or whose position is gone. Also list the shorts with no stop (S2) with the honest options: a stop cannot be attached to an existing position (daily stop order, close and re-enter as a super order, or leave). Cancelled target legs can keep showing PENDING for a while on Dhan: a leg cancelled in an earlier refresh that still shows PENDING is reported as "cancel sent, not yet cleared", never cancelled again blindly.
   - Legs already past their 3x stop cannot be closed by any skill: list them as "close in the broker app".
   - End with one line: what is orderable tonight, what is blocked, and what needs a decision in the broker app.
6d. **Orders hand-off (only after the board, only on the user's yes).** Ask once: "Proceed to orders for ND? Pick a stage: dh252 exits, dh252 add-ons, dh252 entries, share exits, share entries/averaging, clean-up (the cancel/fix list above), stop orders, or none." Then run each chosen stage by invoking its skill in this order, one stage at a time: `dhan-order` (exits, then add-ons, then entries), `dhan-invest-order-exit` / `dhan-invest-order-entry`, `dhan-superorder` for the Clean-up stage (show the whole clean-up list once for approval, then cancel one order at a time with an explicit "yes, cancel these" naming the exact ids; re-check with `super_list` and report what cleared) and for Part 3 (a new option only when the user names the contract). Rules that never change: the target skill's own checks and its per-batch "yes, place these" confirmation are NOT skipped or pre-answered; the user's yes to this question only starts the stage. Never place during market hours (after-market orders only: if the market is open, say so and stop at the board); never place while a guardrail BLOCK or the trading halt is open; never place from a signal the user has not seen. If the user says none, stop here.
7. **Commit + push only after the user says push.** Stage only `dhan-live/` files (never `.playwright-mcp/`). Message: `Dhan refresh <market date>`.

## Guardrails (hard rules, added 2026-11-09)
- The rebuild now ends with `guardrails.py` (checks and balances: freshness, fill ledger vs holdings, signal logic re-derived, capital/concentration, orders, options, broker separation, kill switch) and `test_guardrails.py` (every check must still fire). Report the line `GUARDRAILS <broker>: OK|WARN|BLOCK` and every BLOCK/WARN it prints in the verify step. The same result drives the banner on the pages and refuses order tickets.
- Settlement timing: Dhan holdings can lag the day's fills; the engine then warns (I3 WARN) and the positions/P&L exclude those stocks until holdings catch up. That is expected; a BLOCK (I3 with no recent buy) is a real missed fill.
- Never commit/push while a BLOCK is open without telling the user and getting their explicit go-ahead.
- `data/trading_halt.json` is the user's kill switch; do not flip it without being asked.

## Rules (do not change without the user)
- Fixed capital base 20,00,000; deposits ignored. Closed-trade P&L is gross of charges.
- Equity only; the option-hedge portfolio and investment portfolio are never dh252.
- Never invent numbers; if a source is missing, say so.
- Zerodha / ICICI are out of scope for this skill.
- Orders are placed only through the step 6d hand-off to the order skills, each with its own per-batch confirmation. This skill never places an order by itself.
