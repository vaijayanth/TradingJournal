# Refresh Zerodha (Nifty F&O Supertrend strategy)

**Tool names.** The Zerodha connector exposes grouped tools in current sessions: `mcp__claude_ai_Zerodha_Mcp__portfolio` (modes holdings / positions / margins), `orders` (list / all_trades / history / place / approval_status), `market` (ltp / ohlc / quote / historical / search / option_chain) and `gtt` (list / place / modify / delete). The older names used below (`get_holdings`, `get_positions`, `get_margins`, `get_orders`, `get_trades` = orders `all_trades`, `get_ltp`, `get_ohlc`, `get_gtts`, `place_order`, `place_gtt_order`, `delete_gtt_order`) mean the same calls; use whichever the session exposes.

Run from the repo root of TradingJournal on branch `claude/beautiful-hamilton-fwa55n`. Needs Python 3.10+ and the Zerodha MCP connector (claude.ai account). Everything lives under `zerodha-live/`. The OLD Google-Sheet dashboard (the "Sheet Dashboard" tab) is separate and untouched by this skill.

## The strategy this skill feeds (user, 2026-11-09)
- Universe: Nifty F&O stocks (`data/fno_universe.json`, re-downloaded from NSE whenever the stored list is from an earlier month). Holdings in any other stock are ignored completely.
- Entry: Supertrend flipped to green within the last 3 trading days (user, 2026-11-23; was today only) and still green, and no open position in the stock. Size Rs 20,000 per position, +Rs 5,000 for every 100 trades (open + closed), floored to whole shares (min 1).
- Exit: Supertrend red, any profit or loss, whole position. Grandfathered: a position held at the baseline cut-off (`baseline_from_sheet.json` -> `cutoff_date`) only gets an exit signal once its Supertrend turns red AFTER that date.
- Add: Supertrend green and the position down 6% or more (P&L <= -6%, same as ND) -> 1/10 of the current quantity (min 1), once every 7 days.
- Fixed capital base Rs 30,00,000. Closed-trade P&L is gross of charges.

## Naming (user, 2026-11-17)
AZ trades one kind of stock: **swing shares** (the Nifty F&O Supertrend stocks). Say "swing-share exits / add-ons / entries" (the Dhan side also has "investment shares", the 10 covered-call stocks: that kind does not exist on AZ). Options are always called options, never "shares".

## Scope (user, 2026-11-09)
- The dashboard's open positions are ONLY the stocks in `data/moved_from_sheet.json` plus positions opened through it later (`zerodha_trades.py buy --entry`). All other Zerodha holdings are ignored, but any holding still blocks a new entry in that stock. `data/excluded_symbols.json` (BSE, BEL, RECLTD) is excluded entirely. The sheet's closed trades are not part of this dashboard.
- When the user moves more trades from the sheet, add the symbols to `moved_from_sheet.json` (and tell them to delete the rows from the sheet); never re-run `freeze_baseline.py`.

## Steps

**Swing-share add-ons switch OFF from 2026-11-30 (user, 2026-11-26; `add_on_off_from` in this broker's `data/rules.json`).** From that date the engine emits 0 add-ons: counts, plans and checklists show `0 add-ons (off)`, never an add-on step. 
1. **Prep.** `git status`, `git pull --ff-only`. Stop and tell the user if the tree has unrelated uncommitted changes. If `data/baseline_from_sheet.json` does not exist, run `python zerodha-live/scripts/freeze_baseline.py` ONCE (never again; re-freezing double counts).
2. **Zerodha login.** Call `mcp__claude_ai_Zerodha_Mcp__get_holdings` with `limit: 1`. If it says to log in (or "Failed to execute"), call `mcp__claude_ai_Zerodha_Mcp__login`, show the user the warning text it returns plus the link, and wait for them to confirm they authorised it.
3. **Holdings.** Call `get_holdings` with no limit (the result is large; the tool saves it to a file and prints the path - read it with Python, never paste it). Write `zerodha-live/data/holdings_snapshot.json` as `{"fetched_at": <ISO now, +05:30>, "source": "...get_holdings (quantity + t1_quantity)", "holdings": [{"symbol": tradingsymbol, "qty": quantity + t1_quantity, "avg_cost": average_price, "invested": qty*average_price, "exchange", "product"}]}` keeping only rows with qty > 0. Keep ALL holdings; the engine drops stocks outside the F&O universe.
4. **Today's trades.** `get_trades` (today only - run this every trading day or the fills are lost). **If days were missed (standing rule, user 2026-11-12): do option B FIRST, without asking.** `get_trades` is today-only, so reconstruct the missed fills from the holdings diff: BEFORE step 3 overwrites it, keep a copy of the previous `holdings_snapshot.json` (or `git show HEAD:zerodha-live/data/holdings_snapshot.json`); for every in-scope stock (`moved_from_sheet.json` symbols plus anything in `zerodha_trades.json` `entry_dates`, and any stock that had a pending AMO BUY in the previous `orders_snapshot.json`) compare the new holdings with the previous snapshot: quantity UP = BUY (a brand-new position or one with a pending AMO entry = `--entry`; otherwise an add-on, no flag); price = the holdings avg cost for a new position, or `(new_qty*new_avg - old_qty*old_avg)/added_qty` for an add-on; date = the first trading session after the previous refresh (use the AMO order's day in the previous order snapshot when there is one). Record each with `zerodha_trades.py buy ...` as below. Skip a pending AMO BUY whose stock is not in holdings (it did not fill). Quantity DOWN or a position gone = an exit: the price cannot be derived from holdings, so do NOT guess it; if a `pending_exits` record exists use the last close as a clearly labelled estimate only after telling the user, otherwise ask for the fill price (Zerodha Console tradebook). State in the report that the fills were reconstructed from holdings (it assumes no other trades happened), then offer the Console tradebook as the exact alternative. If the diff is anything other than clean buys, fall back to asking.
   For each BUY of an F&O-universe stock: `python zerodha-live/scripts/zerodha_trades.py buy --symbol <SYM> --date <YYYY-MM-DD> [--entry]` (`--entry` only when it OPENS a new position, i.e. the stock was not held before today). SELL fills of a position that has a `pending_exits` record: `python zerodha-live/scripts/zerodha_trades.py fill --symbol <SYM> --qty <qty> --price <avg fill price> --date <date>` (whole-position exits only). A SELL with no pending record: tell the user and ask for the position's average cost and entry date before recording; never guess.
5. **Order snapshot.** `get_orders`; rewrite `zerodha-live/data/orders_snapshot.json` (`fetched_at`, `source`, `orders[]` with `order_id, symbol, side, qty, order_type, price (null for market), status, amo, placed`) with the orders still pending/open; drop filled, rejected or cancelled ones. The Dashboard and Live Trading read this for the "Ordered / Not ordered" status. **Also, from the SAME order-list pull (no extra call):** run `python zerodha-live/scripts/cc_orders.py <that saved file>`; it keeps today's option (NFO) orders in `data/cc_orders_today.json`, which step 5e uses to check that a GTT that fired really bought the position back. If the pull was saved to a file, use that file; the order list is today-only, so pull it at the end of the session you are refreshing.
5b. **Option positions (covered call).** Call `mcp__claude_ai_Zerodha_Mcp__get_positions` (no limit; the result is large and is saved to a file - never paste it) and run `python zerodha-live/scripts/cc_positions.py <that file>`. It keeps only stock-option legs with an expiry on/after `track_from` in `data/cc_config.json` (November 2026 onwards since 2026-11-09; earlier expiries are ignored; the positions call returns a day list then a net list, cc_positions.py keeps the net row). No option quotes are pulled.
5c. **Live prices for the strike alerts (MANDATORY every refresh, do not skip).** After 5b, call `mcp__claude_ai_Zerodha_Mcp__get_ltp` with `NSE:<SYMBOL>` for every symbol in `data/cc_positions.json` legs (one call), save the raw output to a scratch file and run `python zerodha-live/scripts/cc_prices.py <file>`. The covered-call engine then uses these (same day only) for near/breached strike alerts; with no same-day file it falls back to the last close, which can be wrong by hours or a day. Always say in the report whether live prices were pulled and at what time.
5d. **GTT list (for the 'No GTT placed' alert).** Call `mcp__claude_ai_Zerodha_Mcp__get_gtts` (large; saved to a file), then `python zerodha-live/scripts/cc_gtts.py <that file>`. Then run `python zerodha-live/scripts/scan_gtts.py`: it checks every active option GTT for invalid ones (stale GTT on a closed contract, wrong side, wrong quantity, duplicates, bad triggers, off-rule stop, early expiry) and the result shows as 'Invalid GTT' alerts and guardrail P5. Report the count and the HIGH ones in the verify step; fixing them is the `zerodha-gtt-order` skill, only when the user asks. A short option leg with no ACTIVE buy-back GTT on its contract raises 'No GTT placed'; without a same-day GTT file that check is skipped (and the page says so), never reported as passed. (`cc_gtts.py` now also keeps the TRIGGERED GTTs, which step 5e needs.)
5e. **Option position scan (user, 2026-11-16).** After 5b, 5d and the orders pull in step 5, run `python zerodha-live/scripts/scan_options.py` (read-only; it reuses `cc_positions.json`, `cc_gtts.json`, `cc_orders_today.json` and `gtt_scan.json`, so it needs no new data calls). It checks every open option leg: A orphaned long legs that hedge nothing, B unhedged short puts (naked calls are by design, counted only), C shorts with no active stop GTT (HIGH when already past 3x), D GTTs that FIRED but did not fix the position (buy-back rejected, unfilled, missing, or the short still open), E active GTTs whose trigger the premium has already passed, F the GTT hygiene findings. It prints a `STALE INPUT` line if any of its four inputs is not from today: if the order list is stale, re-pull it (a GTT that fired after the pull looks "not fixed" until then) before reporting section D. This is the same scan as the standalone `/zerodha-option-scan-signal` skill (`python zerodha-live/scripts/test_scan_options.py` is its self-test).
